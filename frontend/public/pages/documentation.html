Documentation

A short, calm guide to building an API in ApiForge and calling it from anywhere.

Looking for a specific endpoint? This page covers the platform as a whole. Every project also generates its own documentation with its exact tables, columns, routes, and example requests — open it from that project's page.

ApiForge turns a database design into a live REST API — no server code to write. Design your tables, generate an endpoint on top of them, and call it from any app.

How it fits together

1

Design your tables

On your project's page, add tables, columns, and relationships between them.

2

Generate an API

Turn a table — or a join across a few tables — into a GET, POST, PUT, or DELETE endpoint.

3

Call it

From your app's code, or straight from Postman, over plain HTTPS.

Where to go next

Each tab below covers one part of that flow.

An API in ApiForge is a saved query — a GET, POST, PUT, or DELETE definition built on your tables — exposed as its own endpoint.

The four methods

GET Read

Select rows from one or more joined tables, with filters, sorting, and paging.

POST Create

Insert a new row from values sent in the request.

PUT Update

Update rows that match a condition you define.

DELETE Remove

Delete rows that match a condition you define.

Where values come from

Every value in an API — a filter, a column to insert, a condition — can be static or dynamic. A dynamic value is filled in from the incoming request when it's called:

query_param a value from the URL's query string, e.g. ?role=student
body_field a value from the JSON request body (POST / PUT)
route_param a value embedded in the URL path itself, e.g. an id
static_value a fixed value you set once, the same on every call

Choosing what comes back

GET picks its output columns individually, each with its own alias. POST, PUT, and DELETE work differently: you choose their return columns as a single list. Whatever's on that list is what comes back in the response — leave it empty and the write still goes through, but the response is an empty array.

Once an API is generated, it's a normal HTTPS endpoint. Call it from your own code, or paste it straight into Postman — no SDK needed either way.

What a request needs

Method GET, POST, PUT, or DELETE — whichever the API was built as.
URL the full endpoint address, copied from the project's APIs tab.
Headers Content-Type: application/json for POST/PUT, plus x-api-key if the project has authentication enabled.
Body a JSON object with the fields the API expects — POST and PUT only.

Example: reading data

A GET request usually needs nothing but the URL.

GET request
$ fetch('https://your-apiforge-domain/api/username/project/posts')
  .then(r => r.json())
  .then(console.log);

Example: creating data

POST and PUT send a JSON body, and an API key when authentication is on.

POST request
$ fetch('https://your-apiforge-domain/api/username/project/create_post', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'x-api-key': 'YOUR_KEY' },
  body: JSON.stringify({ title: 'Hello, ApiForge' })
});

What comes back

Every method responds with a plain JSON array of row objects, never a wrapped object. GET returns the rows it selected. POST, PUT, and DELETE return only the columns configured to come back for that API, one object per row affected — if that API wasn't set up to return any columns, a successful write still responds with an empty array:

response
[
  { "id": 1, "title": "Hello, ApiForge", "published": true }
]

Calling it from Postman

  1. 1 Create a new request Open Postman and start a new request tab.
  2. 2 Set the method and URL Pick the method (GET, POST, PUT, or DELETE) and paste the endpoint URL from your project's APIs tab.
  3. 3 Add headers, if needed Under the Headers tab, add x-api-key when authentication is enabled, and Content-Type: application/json for POST/PUT.
  4. 4 Add a body, for POST/PUT Under Body, choose raw and JSON, then enter the fields the API expects.
  5. 5 Send it Postman shows the response — a JSON array — right below the request.
💡 Getting a 401? Check that x-api-key is present and correct. Getting back []? That's not an error — on a GET it means no rows matched; on a POST/PUT/DELETE it usually means the write succeeded but that API has no return columns configured.

Authentication is a per-project switch that controls whether callers need an API key to reach your endpoints.

How it works

Auth disabled

Every generated API is open — anyone with the URL can call it. Good for public data or quick demos.

Auth enabled

Every request must include your project's API key, or it's rejected before it touches your data.

Sending the key

When authentication is enabled, include the key on every request as a request header:

x-api-key: YOUR_PROJECT_API_KEY
⚠️ Keep it secret. Anyone with the key can call your project's APIs. If it ever leaks, regenerate it from the project's Settings tab — the old key stops working immediately.

Browser requests & CORS

If your frontend calls the API directly from a browser, add its domain to the project's CORS Origins list, or the browser will block the request regardless of the API key.

A few implementation notes for a deeper integration, and for AI agents reasoning about an ApiForge-backed project.

Route pattern

Every generated API is served under the same predictable pattern:

/api/<username>/<project_name>/<api_name>

A single API name can back independent GET, POST, PUT, and DELETE definitions — the HTTP method you call decides which one runs.

Status codes

Every response uses a plain HTTP status code to say what happened:

200 Success
400 Bad request
401 Invalid API key
404 API not found
500 Server error

API keys, recapped

Scope

One key per project — it authorizes every API under that project, not a single route.

Rotation

Regenerating a key from Settings immediately invalidates the previous one.

Failure mode

A missing or invalid key on an auth-enabled project is rejected before any query runs.

🤖 For AI agents: a POST, PUT, or DELETE definition picks its return columns as a plain array of column IDs, resolved to real column names in the response — not a list of column objects like GET's select does. An empty array means no return columns were configured, and a successful write with none still responds with []. The exact return columns and full parameter list for each route are listed in that project's own generated documentation.
